# 单实例 Hosted 容量样本

本入口为已有本地Linux amd64服务镜像运行有界工作负载，不访问业务卷，不下载镜像、安装工具或执行仓颉程序。服务固定2个CPU配额、1GiB内存上限及256个进程/线程上限；Windows Python客户端经Docker本机端口访问。它用于记录这一环境和负载下的结果，不寻找饱和点，也不换算员工数或提供SLA。

在源码根目录运行：

```cmd
python benchmark\capacity\test_metrics.py
python benchmark\capacity\run.py --image <已有本地镜像> --evidence-dir <源码目录之外的新证据目录>
```

第一项包含真实本机HTTP截断夹具，需要回环连接权限；它核对截断错误可记录、完整索引字段、百分位算法和取样覆盖。第二项需要已有Docker Engine，不需要SDK。`--read-operations`可指定32～1024，默认每次比较128次；调低样本数可能无法覆盖全部64个包，必须同时阅读 `packagesVisited`。

## 负载和计量

- 包数按1、16、64递增，每包4版本。半数包属于命名组织，其余使用默认组织。
- 每个制品为确定性生成的256KiB合成协议字节，共256个制品、64MiB；元数据摘要正确，但包体不是可构建CJP。真实归档与消费端构建另见[团队示例](../../examples/team/README.md)。
- 发布、重复和冲突阶段均为并发8；后两者各32次严格要求409，与当前服务默认8个发布准入名额对齐。旧版重复／冲突阶段曾为16并发，新服务会合法返回429，因此不沿用该阶段吞吐作对比，不重试或将429当作重复409。过载准入验证与本有界样本分开记录。各规模执行8并发读取，64包再比较1、8、32并发。读取先遍历包，再轮换版本；默认128次覆盖64包各两次，另外两轮全量检查覆盖全部256版本。
- 一次读取操作包含顺序读取索引和制品、解析索引并比对完整记录及制品SHA-256/字节。计时包括本机Python、HTTP传输和校验，工作线程内计时，不含提交队列等待；吞吐量使用整阶段墙钟时间。
- 所有读取紧随发布，属于热数据路径，不是冷磁盘、真实内网、TLS或Proxy测量。样本不计入SDK、编译和业务项目时间。
- p50/p95/p99采用nearest-rank。每个阶段保存逐操作延迟、包身份、HTTP状态和有效性；摘要含操作吞吐、样本数与访问包数。`artifactMiBPerSecond`只计算合成制品字节，不包含索引、帧元数据或HTTP开销；拒绝发布阶段也包含提交的包体，不代表成功写入吞吐。

## 正确性和资源保护

64包建立后，并发执行相同版本重复发布和不同内容冲突，均应409；读取与错误发布凭据混合运行，错误发布应401，错误读取令牌同样拒绝。这里的“有效操作”指状态和内容符合预期，不能把预期409/401算作成功发布。

负载结束后核对每个版本的完整索引记录、制品摘要和字节。服务停服后导出只读快照，检查64索引和256制品，共320个文件；重启服务后再次全量检查并比较全部文件摘要。Docker运行身份、资源配额、本机端口和挂载均需核对，内存峰值在cgroup接口可用时记录；CPU和内存的结束时刻快照不是连续采样峰值，也不是仓颉堆内存。

全部资源使用随机归属标签。成功时只清理标签核对匹配的容器和卷，失败保留卷与已写证据并尝试停止本次写入进程。凭据随机生成，只放在进程/容器环境；不保存原始容器环境，保留日志前替换凭据值。

## 结果文件

`summary.json`记录固定镜像/二进制、资源、工作负载、阶段结果与清理错误；`samples.json`保留全部原始样本；`storage-manifest.json`和两份合成数据tar支持重启前后完整性核对。原始文件放在源码目录之外，不纳入公开提交。

某阶段异常会保存失败样本并让整体结果失败；截断HTTP响应不能当作成功读取。成功仅说明这次有界工作负载核对通过，不能证明任意更大规模、长期稳定性、故障下SLA或生产容量上限。实测摘要见[容量样本报告](../../docs/capacity-report.md)。
