# 单实例容量样本与适用范围

2026-10-21，在已有Docker Desktop Linux引擎上执行一次固定有界Hosted负载，完整检查 **10/10 PASS，26.88秒**。工作负载和复验入口见[基准说明](../benchmark/capacity/README.md)。这是本机样本，不是容量上限、硬件推荐、员工数或生产SLA。

## 本次测量

一次读取操作包含两个HTTP请求及客户端完整索引/字节/SHA-256校验，延迟含本机Python和Docker端口转发成本；吞吐采用整阶段墙钟时间。百分位为nearest-rank。

| 场景 | 并发 | 操作/秒 | p50 ms | p95 ms |
| --- | ---: | ---: | ---: | ---: |
| 1包读取 | 8 | 285.37 | 26.57 | 39.64 |
| 16包读取 | 8 | 265.62 | 28.51 | 41.52 |
| 64包读取 | 1 | 52.19 | 17.78 | 43.15 |
| 64包读取 | 8 | 273.41 | 25.97 | 42.04 |
| 64包读取 | 32 | 265.20 | 107.44 | 153.69 |
| 从16增长至64包，发布192个新版本 | 8 | 50.69 | 179.78 | 202.49 |

在这一样本中，32并发没有提高读取吞吐，p95明显上升，不能据“并发更高”推断效果更好。64包和1包的8并发结果只说明此小数据集下的观察，不能外推到数万包、大索引或真实团队网络；单次短测也不能确定稳定饱和点。

已读到的最大cgroup内存峰值为 **253,698,048字节，约241.95MiB**，包括容器计费的相关内存及文件缓存，不是仓颉堆大小。结束时刻CPU/内存快照保留在原始报告，不作为负载期间CPU峰值或资源富余的证明。

## 正确性与证据

共1,600个阶段操作、2,864个阶段内HTTP请求，所有操作符合各自预期。该请求数不含健康、身份和单独错误读取令牌检查。32次重复及32次不同内容冲突应返回409；混合负载中的16次错误凭据发布应返回401。它们属于预期拒绝，不是成功发布。

全量检查在重启前后分别覆盖全部256版本，核对完整索引记录（含包名和依赖）及制品字节；停服快照含64个索引和256个制品，共320文件，重启前后文件集合与摘要相同。清理无错误，原始日志、样本和合成快照留在外层 `test-runs/capacity-20261021/acceptance-final/`。

首轮读取只覆盖64包中的前32包，记录保留在 `acceptance/`，不用于本表；均匀取样的中间记录在 `acceptance-uniform/`。独立静态审查发现截断响应可能绕过失败样本记录、索引字段校验不全，修复后执行本表完整负载。其后仅增加错误JSON行形状校验和每样本TypeError保护，**5/5专项回归通过**，未重复完整负载；`accepted-runner.py`保留测量当时脚本，摘要与原始报告一致。审查复核不等于独立执行基准。

因此，本批提供可复验的短测方法及局部使用依据。真实CJP、消费端冷构建见[团队接入](../examples/team/README.md)各自记录；长期负载、大包/大索引、冷磁盘、Proxy/TLS、实际内网、公有云CI、资源饱和、故障SLA和完整官方测试仍未由此证明。当前没有为实际业务配置限流、自动扩容或发布生产容量承诺。
