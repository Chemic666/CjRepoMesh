# 单实例升级与回滚

本页适用于已有Linux amd64服务镜像和Docker命名卷。采用停服维护窗口：暂停发布和写入任务、保留完整快照、在新卷验证候选，再决定切换。本项目尚未提供自动升级器、自动业务切换或跨任意版本的存储兼容承诺。

## 两种回退方式

| 方式 | 数据范围 | 使用条件 |
| --- | --- | --- |
| 旧服务读取新版卷 | 可以保留新版写入 | 必须对这两个具体版本验证存储兼容，先保留新版卷快照；未知格式或迁移不可假设兼容 |
| 旧服务读取升级前快照恢复卷 | 只有快照时点的数据 | 恢复到新的空卷，保留故障卷；快照之后的发布需要另行核对与恢复 |

暂停发布的维护窗口可以防止候选试运行期间产生未纳入旧快照的正式写入。读取令牌和发布令牌沿用原值；不要重新初始化 `.env`，也不要把新随机项目名误当成旧部署。升级镜像、部署配置与存储卷是三个独立对象，都应记录身份。

## 实际维护顺序

1. **核对产物和部署。** 保存原镜像完整ID、服务端摘要、实际挂载卷名、端口、Compose项目名和部署配置。原凭据以原保护权限单独保管，不写入工单或公开日志。候选离线包先运行 `verify.py`，导入本地镜像后再运行 `verify.py --docker`；不使用浮动标签代替产物身份。
2. **停止全部写入。** 暂停发布端、Mirror/Sync及其他写入任务；停止确认属于本部署的服务，检查没有运行容器以可写方式挂载该卷。只停止HTTP接入不能保证后台任务已停止。正常Compose停止不加删除数据卷的选项。
3. **备份完整数据。** 停服后保存完整 `index/` 与 `artifacts/`，包括组织子目录，另行保护配置和凭据。记录文件集合、每文件SHA-256和备份本身摘要，并验证归档路径及类型。只有镜像、只有索引或仅备份单个包都不够。
4. **恢复至新空卷。** 先检查目标卷为空，再恢复完整快照，核对文件集合和摘要。不要覆盖原卷，不让两个服务同时写同一卷。显式指定恢复卷，核对容器实际挂载；不要仅凭容器名或项目名推断卷身份。
5. **验证候选。** 使用固定候选镜像、原读写凭据和已核对的配置启动恢复卷。保持本机监听和原运行权限限制。除健康检查，还要验证匿名读取拒绝、读写令牌区分、默认及所用组织包的索引与制品摘要、重复发布拒绝，并用实际项目做冷缓存构建运行。隔离副本允许发布合成探针；维护窗口内不开放正式发布。
6. **选择切换或回退。** 候选检查通过后，核对业务配置和所选卷，再安排实际入口切换；恢复写入前保留旧镜像、原卷和快照。失败时先停候选，保留日志与故障卷；仅在已验证的版本组合上采用兼容降级，否则从升级前快照恢复新空卷，再启动原镜像并验证。
7. **恢复写入并保留证据。** 核对当前镜像、挂载、凭据、包内容及真实客户端任务后再恢复发布。快照恢复不包含后来写入时，应明确列出缺失版本并由维护者决定如何恢复，不自动覆盖同名同版本。原卷和备份的保留期由实际维护流程决定，不能照搬测试脚本的清理逻辑。

以上是操作顺序。下面的入口只创建合成测试实例，不接收业务卷名，不会替实际部署完成备份或切换；真实维护仍需按部署核对全部参数。Windows原生仓颉执行当前暂停，本文不要求修改系统防护或防火墙。

## 可复验演练

先具备两个不同的本地Linux amd64服务镜像，以及已有真实 `cjpm bundle` 输出：默认组织包作为升级前数据、命名组织包作为候选后新增数据。没有安装或下载步骤，不在Windows执行仓颉程序。从源码根目录运行（占位参数应替换为本机已有产物）：

```cmd
python integration-tests\recovery\upgrade.py --previous-image <旧本地镜像> --candidate-image <候选本地镜像> --seed-package <默认包target目录> --new-package <组织包target目录> --evidence-dir <新的证据目录>
```

入口将镜像引用固定为完整ID，要求服务端二进制也不同。创建随机归属标签的三个新卷，使用动态本机端口和临时读写令牌；凭据只传入进程/容器环境，不保存原始容器环境。辅助归档容器无网络，导出卷只读，服务非root、根文件系统只读、丢弃capabilities并禁止权限提升。恢复只接受本次拥有且为空的卷；成功仅删除本次标签核对匹配的资源，失败保留卷和证据并尝试停止本次写入进程。

14个检查点覆盖固定产物身份、旧版真实发布与私有读取、停写、完整快照、新卷恢复、新版读取及组织包发布、旧版读取新版数据、兼容降级文件不变、受控启动失败、独立快照恢复、快照之后写入缺失、新发布与重复拒绝、恢复实例重建持久化、原卷/候选卷/备份互不影响。启动失败通过无效上游配置触发，不模拟写入中崩溃或格式迁移。

`summary.json`记录实际步骤、镜像及二进制身份、真实包摘要、耗时和清理错误。`before-upgrade.tar`与逐文件清单用于交叉核对；所有材料含合成包数据，仍应留在内部证据目录。成功的文件集合/摘要相等不代表断电持久性或任意版本兼容。
