## 1. 官方原文

### 1.1 主要交付内容

1. 为 cjpm 提供多仓配置及优先级查找能力；
2. 适配多仓依赖解析、冲突处理和版本强制替换；
3. 提供私有中心仓一键部署工具；
4. 支持镜像仓、代理仓及仓库间同步。

### 1.2 关键验收指标

> 多仓机制不得破坏原有依赖解析规则；私有中心仓能够部署、运行并完成镜像、代理或同步等核心场景验证。

### 1.3 推荐指数

五星。推荐指数表示官方推荐程度，不等于自动加分，也不代表同题竞争较弱。

## 2. 解释原则

1. “不得破坏原有依赖解析规则”是最高优先级约束。多仓层只决定从哪些仓库获得候选包，不重新发明 cjpm 的版本求解算法。
2. 官方交付项中的“镜像仓、代理仓及仓库间同步”按三项都需要提供可运行能力处理，不能仅凭验收描述中的“或”主动删去其中两项。
3. “冲突处理和版本强制替换”优先复用 cjpm 已有依赖解析和 `[replace]` 语义，只补充多仓来源相关行为。
4. 初赛只承诺可稳定复现的能力。没有实现的扩展必须明确标注，不在 README 或演示中制造完成假象。

## 4. 初赛范围

### 4.1 必须完成（P0）

- cjpm 官方源码能够构建并运行基线测试；
- 旧单仓配置完全兼容；
- 多仓配置和确定性优先级查询；
- 公共仓与私有仓混合解析；
- 原 cjpm 版本解析、冲突处理和 `[replace]` 语义继续生效；
- 私有仓一键部署，具备发布、查询、下载和持久化；
- 代理仓最小闭环，包括命中、未命中和离线缓存；
- 指定包清单的镜像；
- CjRepo 到 CjRepo 的增量同步；
- 官方要求对应的自动化测试、复现步骤和演示脚本。

### 4.2 冲奖增强（P1）

- Namespace 独占路由，防止私有包被公共同名包替代；
- 安全感知回退：401/403/TLS/校验失败不静默切换；
- 解析来源、回退和替换决策的结构化日志；
- `cjpm repo explain <package>`；
- `cjpm repo doctor`；
- 来源和校验和记录，但不在初赛强行修改正式 lockfile 格式；
- 兼容性差分报告、故障注入报告和真实 Benchmark。

### 4.3 初赛明确延期（P2）

- Dashboard；
- MCP、Agent 与自然语言运维；
- RBAC、SSO、多租户；
- S3/OBS/MinIO 存储；
- 分布式部署、Kubernetes、数据库集群；
- 无官方目录协议支撑的全量中心仓镜像；
- 对外承诺稳定的新 lockfile 规范。

## 5. 关键技术决策

### 5.1 Router 的插入位置

推荐调用关系：

```text
Dependency Requirement
        │
        ▼
Repository Router
        │  候选版本 + 来源
        ▼
Existing cjpm Dependency Resolver
        │
        ▼
Resolved Dependency Graph
```

Router 不负责重新定义版本兼容、最高版本选择、回溯或依赖图合并。

### 5.2 缓存键

缓存必须包含仓库身份，至少满足：

```text
registry + organization + package + version
```

否则不同仓库中的同名同版本制品会互相覆盖，无法证明多仓解析正确。

### 5.3 Mirror 的可交付定义

现阶段未在 cjpm 客户端协议中发现全量包目录或增量变更流。因此初赛的 Mirror 定义为：

> 根据显式包清单主动拉取并校验指定包及版本，而不是宣称能够完整复制官方中心仓。

全量镜像只有在组委会提供额外协议或数据接口后再进入范围。

### 5.4 强制替换

不得先设计独立的 `repository.overrides` 并与 `[replace]` 并存。应先验证如何让既有 `[replace]` 在多仓来源下工作；只有现有表达能力不足时才以最小增量扩展。
