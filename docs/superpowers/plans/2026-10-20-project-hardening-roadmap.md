# CjRepoMesh 工程完善路线图

> 本文是跨阶段路线图，不是所有阶段的代码级实施说明。各阶段启动时，根据源码和复现证据细化任务，不把待核查项直接视为缺陷。
> **For agentic workers:** Use superpowers:executing-plans when implementing a scoped stage. Do not start later stages merely because they appear in this roadmap.

**Goal:** 在保留现有 cjpm 语义和已交付能力的基础上，形成可靠、易诊断、可复验的单实例私有仓与多仓客户端交付版本。

**Architecture:** 继续复用原 cjpm 求解器；多仓层负责候选与来源。服务端保持仓颉进程加文件系统；优先修复现有链路，再根据实际价值增加必要的诊断能力。

**Tech Stack:** 现有仓颉与 stdx、PowerShell、Python 标准库、项目已有 Docker/WSL 验证环境。

**Spec:** `docs/competition-requirements-matrix.md`、`docs/architecture.md`。这些文件含历史快照；提交状态以用户确认及最新证据为准。已收到参赛者转发的决赛准备通知，完整赛制与评分尚未独立核查。

## Global Constraints

- 保留 `cjrepomesh-multirepo` 及现有未提交成果，不向上游 `origin` 推送。
- 历史2026-10-20授权只限当批；参赛者已于后续明确授权本项目阶段验收后持续自主Commit和双端Push，沿用main及GitHub独立noreply历史。仍不包括origin、强推、历史改写、PR或Release，见交付记录。
- Windows 工作区为源码来源；已有 WSL/Docker 仅用于必要的构建和验证。
- 不绕过 Windows Application Control；无法验证的项目保留明确阻塞状态。
- 不更换原求解器、不改官方 lockfile 规范，不默认引入数据库或分布式系统。
- 个人信息、签字和提交材料留在私有目录，不进入公开仓库。
- 不将历史通过记录当作当前产物验收，不将 Maple 子集称为完整 HLT/LLT。
- 一般改动运行相关验证；候选交付版本才运行必要的综合验收。
- 按参赛者的持续开发要求，完成子项后直接推进路线内下一优先缺口，阶段进度不作为等待“继续”的门槛；仅重大取舍、外部权限或范围变化需要用户参与。

## Review Focus

- 401/403、独占路由和校验失败不能被回退或重试绕过：阶段 3 验证。
- 启动脚本不能误认其他进程的健康响应，也不能停止无关进程：阶段 2 核查并复现。
- 索引不能宣告尚不可用的制品；失败重跑不能静默覆盖冲突版本：阶段 4 验证。
- 诊断、状态文件和日志不能泄露令牌或含凭据 URL：阶段 2、5 核查。
- 缓存或来源记录不能让不同仓、组织、同名同版本互相污染：阶段 3、4 验证。

## 顺序、范围与停止条件

主线：1 → 2 → 3 → 4 → 5 → 6 → 7。阶段 2–4 出现阻断级缺陷时优先处理，不机械等到后续阶段。

本轮不默认开发 Dashboard、MCP、SSO/RBAC、多租户、对象存储、分布式协调、字节级断点续传或无目录协议支撑的全量镜像。新增需求需有真实场景与独立范围。

用户已授权在本路线范围内连续推进，无需逐次说“继续”；本批另获明确 Commit/Push 授权，只同步两个参赛仓库，不向 origin 推送、不创建 PR/Release 或增加范围外的新系统。2026-10-20 已形成当前补强候选，部署、多仓、恢复、诊断、跨平台和受影响官方兼容性验证已记录。完整 HLT/LLT、独立备份灾难恢复演练、断电持久性及分布式协调不在通过范围内；后续交付仍按实际授权执行。

准确工期在阶段 1 后估算，取决于实际缺陷和构建环境。优先保证阶段 2–4 的正确性，不承诺固定日期完成完整 Maple。
