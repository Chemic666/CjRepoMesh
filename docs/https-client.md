# HTTPS客户端与服务端出站身份验证

> 当前候选身份与实际执行范围统一见[固定候选清单](candidate-acceptance.md)首节；以下各批记录绑定各自摘要。ba9b/8fc3原生TLS19/19、24/24已另行执行，不继承旧版本平台/恢复成绩。

证书链验证确认发证方可信，名称验证确认连接的是配置中指定的仓库。这两项都应通过后，客户端才发送包含令牌的HTTP请求。服务端本身仍是HTTP服务；真实团队HTTPS入口需要另行部署和验收成熟反向代理，本文不提供已验证的网关配置。

## 当前客户端行为

`[global]` 的 `strict-tls` 默认true。2026-10-21修复前，当前stdx组合只验证证书链，受信任CA签发的错误仓库名称仍被接受，索引、发布和下载均受影响。修复后这三个路径共同使用以下校验：

- DNS地址：将解析后的主机名交给TLS配置，保留原生证书链、有效期和服务器用途检查，并验证名称。
- IP字面量：当前stdx的名称接口使用DNS校验，直接传IP会错误拒绝合法IP SAN。客户端先完成默认TLS握手，再将叶证书的IP SAN与目标IP二进制地址精确比较，通过后才把连接交给HTTP层；没有切换成替代默认证书链的自定义认证回调。
- `strict-tls=false`保留已有显式兼容语义，会关闭身份校验，不作为本次HTTPS接入的使用方式。普通HTTP本机部署不获得TLS保护。

索引、发布和下载请求均不自动跟随重定向。配置应直接指向仓库实际端点；遇到重定向时先核对仓库或网关地址。默认库虽会移除跳转请求的Authorization，但307/308仍可能转发发布包体到其他地址，包括明文HTTP，且跨主机跳转不能继续套用原仓库身份。客户端因此明确拒绝自动跳转，不通过关闭严格校验处理这类配置问题。

API说明可参考[官方TLS配置接口](https://gitcode.com/Cangjie/cangjie_stdx/blob/main/doc/libs_stdx/net/tls/tls_package_api/tls_package_structs.md)；该链接随上游更新，本文结论以当前固定SDK/stdx和实际客户端产物为准。

## 服务端出站HTTPS

服务端Proxy/Mirror/Sync现也支持HTTPS源仓及Sync目标：共享GET与发布POST分别绑定各自URL，DNS名称用TLS配置验证，IP在默认链/有效期/服务器用途检查后精确比对叶证书IP SAN；验证成功前不把连接交给HTTP层。不提供TrustAll开关，不跟随跳转。服务监听入口仍是HTTP，不能把出站HTTPS当成入站网关完成。

原生Linux进程在启动前设置 `SSL_CERT_FILE` 为可信CA文件路径即可；私钥不交给仓库进程。默认TCP建连30秒（可用 `CJREPO_CONNECT_TIMEOUT_SECONDS` 调整1–300），TLS握手另用stdx的30秒读写等待。后者是每次I/O等待设置，不是握手总预算；DNS、慢速分片握手及完整操作绝对时限没有因此获得保证。

离线镜像具有TLS库但不带公共根CA集合。新七文件工具包可在首次配置时用 `configure.py --ca-file` 导入可信PEM证书，固定只读挂载至容器，SSL_CERT_FILE使用容器内路径；仅在.env设置宿主路径仍不够。默认不导入CA时保持空trust目录，Hosted接收走本机HTTP。证书来源仍由团队可信渠道确认，不通过关闭身份校验处理文件或证书问题，见[初始化与运行诊断](../deployment/portable/README.md)。

服务端专项：`python3 integration-tests/compatibility/server_tls_identity.py --server <Linux服务端> --package-dir <已有真实默认组织CJP及meta-data.json目录> --evidence-dir <新证据目录>`。使用已有OpenSSL和匹配SDK/stdx；原18项包含Mirror/Sync的可信DNS/IP、Proxy可信IP、未知CA/错误DNS/IP/仅clientAuth用途拒绝，以及先成功读取索引、再遇到错误制品或发布连接证书的检查。记录HTTP到达阶段、认证、真实发布帧及失败存储保持；Sync发布正向是协议夹具，不证明夹具持久化。

## 团队CA与任务环境

仓库地址必须与证书DNS名称或IP SAN匹配，不能把一个域名的证书用作任意地址证书。根证书通过团队的可信渠道提供，私钥不交给客户端。真实发布与读取令牌仍由CI受保护变量注入，配置只引用 `token-env`。

本批Linux验证通过进程环境的 `SSL_CERT_FILE` 提供测试CA；没有向操作系统信任库安装证书。已有正确CA文件时，可在加载SDK的受保护Linux任务环境中为[团队示例](../examples/team/README.md)设置该变量：

```bash
SSL_CERT_FILE=/secure/team-ca-bundle.pem bash run.sh
```

该设置只作用于本次任务及其子进程，不应设置为来源不明的证书文件。Windows证书存储、全新主机及实际企业CA分发没有在本批验收，不将Linux做法直接推广为它们的验证结论。

证书不受信任、名称不符、用途不符与401鉴权失败是不同问题。先核对实际访问地址、证书和CA来源，再核对令牌角色；不要通过关闭严格校验处理错误证书。

## 可复验验证

加载已有Linux SDK和OpenSSL环境，提供增强客户端及已有真实 `company::teamhello 1.0.0` 打包目录，从源码根目录执行：

```bash
python3 integration-tests/compatibility/tls_identity.py \
  --cjpm /path/to/enhanced/cjpm \
  --package-dir /path/to/teamhello/target \
  --evidence-dir /path/to/new-evidence-directory
```

入口只绑定本机随机端口，用Python HTTPS协议夹具生成一天有效的合成CA及正向叶证书，另生成已过期叶证书并用OpenSSL确认error10。证书私钥在Linux0700临时目录、0600文件中，退出时删除；CA路径只给客户端子进程。各用例隔离HOME与缓存，保留证据前脱敏，不更改系统信任或网络策略。

原15项包括：可信IP索引、不可信CA拒绝、错误名称索引拒绝、可信TLS发布请求、错误名称发布拒绝、索引成功后制品连接证书错误拒绝、真实CJP下载构建运行及来源摘要、可信TLS上的错误令牌401、可信DNS名称、错误IP SAN、错误DNS名称、仅有clientAuth用途的证书拒绝，以及302索引、307发布、307下载三种自动跳转拒绝。身份错误用例核对应用层没有收到请求；下载错误用例只允许先前受信任的索引请求，不能留下成功来源记录。跳转用例先确认DNS localhost HTTPS入口确实返回对应状态，再确认命令失败、明文HTTP目标没有收到请求且无成功来源记录；下载项须先通过索引，避免用提前失败冒充拦截成功。

当前默认扩为19项，另加过期IP索引、DNS索引、发布和正常索引后过期的下载连接。四项都必须在实际握手中收到certificate_expired告警，核对其用例标签，不凭非零退出通过；下载项还要求只有索引HTTP且没有成功来源记录。可加 `--expiry-only` 只执行这四项，不能将4/4当成默认19项或原综合清单通过。

该HTTPS入口是验证夹具：发布响应只证明请求经验证的TLS连接送达，不证明真实Server存储发布。真实服务端发布与团队CI在前序独立记录中；本批只从真实CJP验证客户端的HTTPS下载、编译与运行。没有部署生产反向代理、执行跨主机通信或提供自动签发/更新证书功能。
