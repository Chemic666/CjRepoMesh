# CI仓库来源基线

来源记录回答“上次解析选了什么”；基线检查回答“本次选中的仓库依赖是否全部符合独立批准的记录”。该功能需要包含来源基线修订的增强客户端，不含此功能的旧客户端会忽略环境变量。新版团队消费脚本会先检查能力，使用前仍须核对[当前客户端身份](candidate-acceptance.md)。默认不启用，不改变原版本求解和官方lockfile格式。

## 批准与启用

在受控环境完成一次预期构建，结合项目依赖、lockfile、仓库配置及可信制品摘要，独立审核 `cjpm-provenance.json` 的全部仓库包，包括传递依赖。经审核的副本放入CI受保护位置，保持 `formatVersion = 1` 和原有 `packages` 格式。五个字符串字段为 `package`、`version`、`repository`、`registry`、`sha256`；摘要必须是64位小写十六进制。保管内部仓库地址，文件中不要放凭据。

批准文件应独立于每次构建的可写输出，最好位于项目/打包目录之外并只读挂载。禁止用本次生成的记录覆盖批准文件，也不要在每个CI任务开始时自动复制当前输出作为批准步骤。保护基线及环境变量，避免不可信变更替换基线或取消检查；仓库配置、工作目录和工具链也属于信任边界。

在[只读消费任务](../examples/team/README.md)加载现有SDK并设置读取凭据、客户端路径之后：

```bash
export CJREPOMESH_SOURCE_BASELINE=/protected/team-source-baseline.json
bash run.sh
```

变量也可用于直接调用增强版 `cjpm build`；相对路径按当前依赖分析根目录解释，CI推荐绝对路径。变量未设置时保持原行为，显式空值会拒绝。不要给具有另一套仓库依赖图的发布任务直接复用消费端基线。

## 消费任务的客户端能力前置检查

使用可信渠道交付的客户端，可先离线执行：

```bash
/path/to/cjpm repo supports source-baseline-v1
```

支持时退出0，stdout仅一行 `source-baseline-v1`；未知标记退出1，诊断不回显输入。这个精确查询不需要SDK，不读取项目或仓库配置，不运行构建脚本、不解析依赖或访问仓库，也不校验批准文件。`repo supports --help` 和 `repo supports -h` 被视为未知标记；查看帮助使用 `repo --help`。额外参数不属于离线查询，仍走普通命令预检。

新版[团队消费脚本](../examples/team/consumer/run.sh)在基线变量已设置时（包括显式空值），先要求能力查询退出0且stdout严格匹配标记；不支持、空/错误/多余stdout或非零均在 `build` 前退出2，提示使用已验证的兼容客户端。完整客户端启动器的完整性信息位于stderr，不影响这个协议；查询失败时可单独执行受信包的完整性验证和上述命令排查。未设置基线变量时不查询能力，保留原流程；能力通过后，空值或基线文件错误仍由构建时原检查拒绝。

8da5客户端已有基线检查，但没有这个新查询，因此也会被新版受保护消费任务拒绝；需升级至含查询的新客户端。更早不具备基线功能的客户端同样不能通过。直接调用 `cjpm build` 不会由示例脚本代做此前置检查，不能仅设置变量就假定任意客户端会执行准入。

能力响应只用于避免误配旧客户端，不认证二进制或启动器来源；恶意替换程序仍可伪造响应。继续使用可信分发与既有完整包清单校验，不自动批准或覆盖基线。

## 检查与失败行为

在原求解器确定最终仓库依赖及选中的 `[replace]` 项后、启动本次仓库制品下载任务前，逐项比较完整包集合、版本、仓库配置名、原始仓库URL及SHA-256；数组顺序不影响结果。空仓库图只能匹配空包集合，已有源码缓存也不会跳过基线检查。元数据索引访问和缓存写入可能在检查前发生。

设置为空、文件缺失/不可读、超过1MiB、JSON/字段类型错误、未知格式、重复包、空必需字段、不安全地址或任一来源失配均拒绝。文件不得与当前 `cjpm-provenance.json` 或 `cjpm-provenance.json.tmp` 相同，也不得经规范路径/符号链接指向它们。错误返回非零，消息以 `repository source baseline rejected` 说明类别，不回显基线路径、原始内容或字段值。

拒绝时不启动本次分析的仓库制品下载，不覆盖之前的来源输出，也不修改批准文件。这里的“本次分析”不等于整个构建命令：前一个已获批准的脚本依赖图可能已经下载制品并写入来源输出，后一个主图失败不会撤销这些操作。更换版本、仓库、URL或摘要时，需要重新审核批准文件；排障先核对配置和依赖变化，不把关闭检查作为默认修复方式。

## 工作空间与构建脚本

同一次依赖分析会合并所选工作空间成员的仓库依赖及其传递依赖，基线须匹配这个完整集合。`--member` 改变所选成员，也可能改变集合；不能假定整工作空间基线适用于每个成员。独立审核不同构建入口的基线，在CI任务中绑定对应的绝对路径，例如：

```bash
# 在工作空间根目录执行；文件名只用于说明两个独立批准的入口。
CJREPOMESH_SOURCE_BASELINE=/protected/workspace-full.json /path/to/cjpm build
CJREPOMESH_SOURCE_BASELINE=/protected/workspace-app-a.json /path/to/cjpm build --member app_a
```

`build.cj` 存在非空 `script-dependencies` 时，脚本依赖会另行求解，每个图都与同一环境变量指定的完整基线比较。不要把不同图简单合并成更大的批准集合，或自动按当前图筛选批准条目；精确集合检查会拒绝这种用法。

| 已实跑场景 | 行为 |
| --- | --- |
| 两成员分别使用meshdep和parent→meshdep | 整图的两个包基线可构建并运行；不完整集合拒绝 |
| 仅构建直接使用meshdep的成员 | 整图基线拒绝；该成员自己的单包基线可构建并运行 |
| 仅构建parent→meshdep成员 | 两包基线可构建并运行 |
| 脚本与应用都使用parent→meshdep | 同一两包基线分别匹配，pre/post脚本与应用均执行成功 |
| 脚本仅使用meshdep，应用使用parent→meshdep | 两包基线在脚本图拒绝，未执行脚本、未下载制品；此种异图接入不支持 |
| 脚本没有仓库依赖，应用来源漂移 | pre脚本已执行，主图拒绝且零仓库制品请求，不执行post脚本 |
| 单包基线批准脚本图，随后两包主图拒绝 | 已下载一次meshdep、执行pre脚本并保存脚本图来源；主图不下载、不执行post，批准文件不变 |

上述同图脚本和工作空间整图也验证了根目录相对基线路径；CI仍推荐绝对路径。脚本无仓库依赖不代表脚本安全；多图构建的最终 `cjpm-provenance.json` 也不是整条命令的事务日志，命令失败后可能保留前一个成功图的记录，不能据此判断构建成功。需要不同脚本图与主图同时接入时，应先评估这一限制，不能通过关闭检查、放宽为子集匹配或自动批准本次输出来绕过。

## 能力边界与复验

接收端[停服备份和独立恢复](../deployment/portable/README.md#接收端停服备份与独立恢复)不会修改批准文件。当前组合已对一个包含Hosted内部组织包及Proxy包的双包图完成恢复后空缓存基线匹配/漂移拒绝；受控容器环境保持原仓库URL。迁移到不同地址仍需独立审核目标基线，不能因恢复成功自动批准地址变化；这不扩大为异图脚本支持。

这不是签名/发布者身份认证，也不重新验证已解包源码缓存、Git/本地依赖、SDK或编译结果。它不提供构建脚本沙箱或“检查前零代码执行”保证。多图仅验证上表选定的Linux场景，不代表任意工作空间、嵌套本地/Git依赖脚本、增量脚本缓存或多版本冲突均兼容。硬链接别名、恶意并发文件替换不属于保证，应使用受保护的工作目录、独立基线和隔离缓存。

Linux真实两层CJP、匹配/替换/热缓存及非法输入回归入口是 `integration-tests/compatibility/source_baseline.py`；多图入口为 `integration-tests/compatibility/source_baseline_graphs.py`。使用方法见[构建与验证说明](../integration-tests/README.md)。当前产物的实际执行结果以[验证记录](verification-report.md)为准，不扩大为Windows或完整Maple验收。
