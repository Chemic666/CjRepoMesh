# 部署、升级与恢复操作

本页串起现有操作入口。当前交付范围是单实例仓库；个人信息、签字材料和真实凭据应留在公开仓库之外。

## 首次使用

1. 按 [构建与验证说明](../integration-tests/README.md) 准备已有仓颉 SDK、匹配的 stdx 和平台依赖，不混用 Windows/Linux 二进制。
2. 选择 [Windows 原生部署](../deployment/windows/README.md) 或 [Docker 部署](../deployment/docker/README.md)。固定数据目录或卷，保存部署参数，令牌单独保管。
3. 设置发布令牌。需要私有读取时同时设置读取令牌；客户端用 `token-env`，不要把令牌放进 URL、命令历史或公开配置。
4. 运行相应 `doctor.ps1`。健康检查成功只代表服务可响应，还应实际发布一个测试包、下载并核对 SHA-256，再验证客户端构建。
5. 多仓项目按 [配置说明](multirepo-implementation.md) 设置地址、优先级和路由。内部包使用独占路由时，公共仓不会作为后备。

## 升级前保留什么

- 当前源码状态或版本、实际二进制 SHA-256，以及对应 SDK/stdx 版本；
- 仓库完整的 `index` 与 `artifacts`，同时保留其组织子目录；
- 部署参数及独立保管的令牌，不只保存一个状态文件；
- 升级前的诊断结果，以及正在运行的 Mirror/Sync 清单。

停止服务和会写入同一存储的 watcher 后，再做冷备份。只复制索引或只复制制品不构成完整备份。Docker 应备份实际持久化卷，不以镜像或容器文件系统代替包数据。当前没有自动备份调度和事务快照工具，不能据此承诺不停机备份一致性。

## 恢复到独立目录

1. 保留故障现场，停止确认属于本部署的服务及 watcher。
2. 将完整备份恢复到新的空目录或独立卷，避免直接覆盖故障数据。
3. 使用对应平台的服务端产物启动恢复副本。Windows 可用 `start.ps1 -Storage <恢复目录>`；需要并存检查时另选端口。不要共享两个进程的可写存储。
4. 运行诊断，读取默认仓与所用组织仓的索引、制品，并将下载 SHA-256 与备份索引比较；验证需要使用的客户端项目后，再安排切换。
5. 保留原目录与备份，直至恢复结果经实际业务检查。

上述文件存储冷备份流程已在 Windows 与 Linux 各完成一次独立演练：使用真实 cjpm 包，停服后复制完整存储并核对文件集合与 SHA-256，使原路径离线，再从新目录恢复；验证私有读取、默认/命名组织包、全新缓存下构建运行、再次发布和重启持久化。复验入口见 [冷备份恢复专项](../integration-tests/recovery/README.md#cold-filesystem-backup-and-restore)，实际产物与证据见 [验证报告](verification-report.md)。

演练的清单对比能发现测试副本的制品损坏和索引缺失，不代表服务提供自动备份校验。凭据与部署参数仍需独立保管。

Docker 命名卷另已完成停服 tar 导出、新卷恢复及真实客户端构建的独立演练（9/9）；流程与复验入口见 [Docker 部署说明](../deployment/docker/README.md#冷备份与恢复验证)。演练不操作现有业务卷，也不执行业务切换。在线快照、自动调度、业务切换和断电持久性尚未验证。

## 按故障类型处理

| 现象 | 检查与操作 |
| --- | --- |
| 启动提示端口占用或进程身份不符 | 核对占用者、路径和启动时间，不删除活跃状态文件来绕过检查；旧状态迁移见 Windows 部署说明 |
| 401 / 403 | 检查源读取、目标读取和目标发布令牌各自用途，不通过公共仓回退绕过 |
| 404 / 5xx | 用 `cjpm repo doctor <包名>` 查看各允许仓库；独占路由不会跨仓回退 |
| 网络超时、连接失败或响应损坏 | 修复网络或上游响应后重试；这些错误当前停止解析，不隐式切换来源 |
| 发布中断 | 重发同一版本及相同内容。只有匹配的索引/制品缺失状态可补齐，完整重复和冲突仍返回 409 |
| Sync 中断或响应丢失 | 重跑原条目或清单。目标完整时跳过，缺失制品可补齐；损坏或冲突内容明确失败，不自动覆盖 |
| 历史来源地址不安全 | 保留原记录，在配置中移除 URL 凭据，改用 `token-env`，成功构建后重新生成来源记录 |
| 原生服务端或 Mirror/Sync 提示 invalid URL | 使用无凭据、查询参数和片段的 HTTP(S) 基地址；认证改用相应 `CJREPO_*TOKEN` 环境变量；非法地址的 watcher 会直接退出，修正配置后再启动 |
| 仓库名称改指向无关服务 | 更换仓库名称并使用新的缓存根目录；旧单仓 `home` 至少更换缓存根目录，避免沿用旧来源内容 |

`cjpm repo explain <包名>` 解释当前候选选择；`--recorded` 读取上一次成功构建的来源记录，不代表实时仓库状态，也不是官方 lockfile。

## 停止与卸载

Windows 使用 `stop.ps1`，Docker 使用 `down.ps1`，默认保留包数据。卸载程序前核对存储实际位置并保留备份。Docker 的 `-PurgeData` 会删除持久化数据，不用于普通升级或排障。

每批产物的实际通过范围与未验证事项见 [验证报告](verification-report.md)，不能把历史测试记录视为当前版本验收。
