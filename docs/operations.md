# 部署、升级与恢复操作

本页串起现有操作入口。当前交付范围是单实例仓库；个人信息、签字材料和真实凭据应留在公开仓库之外。

## 首次使用

### 固定双包的首次接入

当前接收路径使用[候选清单](candidate-acceptance.md)首节的21文件Linux客户端团队包与9文件服务端包。公开仓库提供源码、工具及摘要，不包含SDK、交付归档或凭据；由管理员通过受控渠道提供完整包，并独立核对归档和清单摘要。客户端需要已有Linux amd64 SDK1.1.3、stdx1.1.3.1、Python3.10+及编译链接工具；服务端运行只需已有Python/Docker Compose。不要混用历史包或只复制启动器。

下面串起固定示例company::teamhello 1.0.0的流程。命令中的127.0.0.1示例仅适用于服务与任务确实共享同一回环网络环境的Linux部署。Windows宿主、WSL和容器不必共享回环，不能因为在同一台电脑就沿用此地址；先由管理员确认任务环境中可达且获准的仓库URL，再一致替换发布、消费和批准中的原URL。本文不为套用示例自动修改绑定、路由或来源规则。已有项目应保留自己的源码、依赖和运行入口，不用示例目录或批准文件覆盖它。

1. **接收新服务目录。** 在尚未初始化的服务端包目录，按[服务端接收步骤](../deployment/portable/README.md#接收端首次启动)校验文件、导入image.tar、校验已加载镜像，再configure及显式Compose启动。Docker变为healthy后执行 `python verify.py --running`。已有部署保留.env、项目名和卷，不重跑初始化。读/写凭据由管理员分别私密交付，不把.env发给只读CI。
2. **准备客户端环境。** 在发布和消费的受保护Linux会话中分别执行以下准备，将 `CJREPOMESH_CLIENT` 设为完整工具包的绝对路径，先校验，再加载已有SDK/stdx。使用干净角色会话，不继承其他项目的来源批准设置；SDK环境应在开启严格未定义变量检查之前加载，不安装或修改系统信任：

   ```bash
   export CJREPOMESH_CLIENT=/absolute/path/to/client-bundle
   python3 "$CJREPOMESH_CLIENT/verify.py"
   source /existing/cangjie/envsetup.sh
   export CANGJIE_STDX_PATH=/existing/stdx/linux_x86_64_cjnative/static/stdx
   export CJREPOMESH_CJPM="$CJREPOMESH_CLIENT/run.sh"
   ```

3. **发布受控示例。** 仅给发布会话注入受保护的CJREPO_PUBLISH_TOKEN，使用包外新任务目录。以下绝对路径为待替换占位；生成目录的父目录必须可写：

   ```bash
   : "${CJREPO_PUBLISH_TOKEN:?先由受保护渠道注入发布令牌}"
   python3 "$CJREPOMESH_CLIENT/prepare-team.py" --role publisher --registry http://127.0.0.1:8080 --output /private/jobs/publisher-001
   (cd /private/jobs/publisher-001 && bash run.sh)
   ```

   退出0后核对该任务target中的真实CJP与meta-data.json。重复发布1.0.0返回409时应保留现场，先核对已有版本，不把冲突当成功，也不为了重跑删除仓库数据。
4. **独立批准消费来源。** 维护者审核目标版本与实际CJP的SHA-256，决定是否批准；文件保存在任务输出之外的受保护位置，只读交付CI。固定示例的结构如下，摘要必须替换为独立核对的64位小写SHA-256；不要从本次消费者provenance自动生成批准。repository必须是准备器实际使用的internal，registry须与准备时的原始URL完全一致：

   ```json
   {
     "formatVersion": 1,
     "packages": [{
       "package": "company::teamhello",
       "version": "1.0.0",
       "repository": "internal",
       "registry": "http://127.0.0.1:8080",
       "sha256": "<独立审核的64位小写SHA-256>"
     }]
   }
   ```

   真实项目须批准完整最终图，含传递依赖及选中替换项；主图与脚本图不同时按[分图规则](repository-source-baseline.md#工作空间与构建脚本)分别批准。更换地址、仓库名、版本或摘要需重新审核，不能缩小批准集合来消除拒绝。
5. **单次冷消费。** 在已加载同一工具链的消费会话只注入CJREPO_READ_TOKEN，不配置发布凭据；将CJREPOMESH_SOURCE_BASELINE设为上述批准文件的绝对路径，再准备另一个新目录：

   ```bash
   unset CJREPO_PUBLISH_TOKEN
   : "${CJREPO_READ_TOKEN:?先由受保护渠道注入读取令牌}"
   export CJREPOMESH_SOURCE_BASELINE=/protected/teamhello-1.0.0.json
   python3 "$CJREPOMESH_CLIENT/prepare-team.py" --role consumer --registry http://127.0.0.1:8080 --single-use --output /private/jobs/consumer-001
   (cd /private/jobs/consumer-001 && bash run.sh)
   ```

6. **判定并保留结果。** 任务退出0、应用输出含 `CjRepoMesh team 1.0.0: CI`，且完整来源记录与独立批准一致，才记作该任务成功。保留lockfile、来源记录和受保护日志；provenance本身不证明构建成功。并行CI各用一个全新目录，不共享可写HOME/cache/target。成功或失败后均保留单次领取标记，重试另建目录，不删标记或清缓存复用。

默认服务端包只监听回环HTTP。服务端configure的--ca-file只配置**服务端出站信任**，不会开启入站HTTPS；客户端prepare-team.py的--ca-file/--ca-sha256只配置**任务进程信任**，也不会部署网关。已有且获准的HTTPS入口按[团队CA步骤](../examples/team/README.md#https与已批准的私有ca)传入同一地址、公开CA和独立摘要，不能仅改URL后就认为跨机可用。网络/绑定/来源规则及真实凭据传递另行授权，不沿用历史机器IP、不关闭TLS校验。

| 首次接入失败 | 优先处理 |
| --- | --- |
| 包校验或能力查询拒绝 | 核对完整包与可信清单，使用当前兼容客户端；不修改清单或关闭准入 |
| 401/403 | 核对对应角色令牌及实例；不回退公共仓或把发布凭据交给CI |
| TLS或来源基线拒绝 | 分别核对端点/SAN/CA，或完整图/仓库名/原URL/SHA；保留批准和现场，不自动批准当前结果 |
| 单次守卫退出2 | 保留任务与标记，准备新目录；先查前置错误，不把复用拒绝当编译故障 |

此路径复用已验收的包内团队及并发流程；本文命令检查不代表在新主机或实际团队环境重新验收。首次接入后，按本页后续步骤选择诊断、停服完整备份/恢复或依赖快照，保留原数据与凭据。

### 源码开发与其他部署入口

1. 源码构建按 [构建与验证说明](../integration-tests/README.md) 准备已有仓颉SDK、匹配的stdx和平台依赖，不混用Windows/Linux二进制。已有[离线服务端包](../deployment/portable/README.md)时，服务端运行只需Python 3与Docker Compose；开发者构建仓颉应用仍需工具链。
2. 源码开发入口保留[Windows原生部署](../deployment/windows/README.md)和[开发镜像部署](../deployment/docker/README.md)；本机当前暂停Windows仓颉执行，固定包接收不需要重新构建。固定数据目录或卷，保存部署参数，令牌单独保管。离线包的 `.env` 同时固定项目名，重建时保留；Compose命令始终显式 `-f compose.yaml`。
3. 设置发布令牌。需要私有读取时同时设置读取令牌；客户端用 `token-env`，不要把令牌放进 URL、命令历史或公开配置。
4. 新离线包在Docker显示healthy后运行 `python verify.py --running`；原生/开发镜像部署使用相应 `doctor.ps1`。诊断会核对本部署身份，不能仅凭HTTP响应认定正确。成功后仍应实际发布一个测试包、下载并核对 SHA-256，再验证客户端构建。
5. 多仓项目按 [配置说明](multirepo-implementation.md) 设置地址、优先级和路由。内部包使用独占路由时，公共仓不会作为后备。

开始接收前先确认 `docker compose version` 可用。隔离用户目录可能同时隐藏已有Compose插件位置，表现为Docker本身可用但compose命令不可用；应先解决本机现有插件发现问题，不修改交付清单来绕过校验。服务端接收工具只接受普通交付文件，不能把 `verify.py` 或 `configure.py` 链接到另一份包。更新接收工具后领取新的完整归档；原包、已有凭据和业务数据保留。

`verify.py --running`只读检查原项目、实际容器/卷、精确回环绑定、运行中二进制及已列权限约束，不修复或启停服务；与检查已加载镜像的 `--docker` 模式互斥。HTTP就绪可能早于Docker健康状态，starting时先等待。新诊断器还在内存中比对Compose实际解析的配置与运行实例读写令牌，发现.env修改未应用会失败；不输出或保存含凭据的原始Compose配置。它不替代真实认证读写测试，先核对变更，再决定是否重建；不要为通过诊断自动覆盖凭据。旧离线包可能没有运行态或令牌比对检查，应领取新的完整包，不能只替换脚本破坏清单。

## 开发者发布与CI接入

已有[Linux客户端离线包](../deployment/client/README.md)时，先在接收目录执行 `python3 verify.py`，再通过完整路径调用 `run.sh`。帮助和修订后的 `repo explain <包名> --recorded` 可无SDK运行；版本、在线来源解释、仓库诊断及构建仍需加载匹配SDK/stdx。启动器只为本进程设置运行库路径，不修改系统配置；归档完整性摘要需要经可信渠道核对。

离线排障时，在包含 `cjpm-provenance.json` 的目录执行客户端包的 `run.sh repo explain meshdep --recorded`；记录可以只读，源仓可以停服，不要求项目源码或编译器。原仓库配置检查仍保留，无效配置先修正；命令不会把损坏记录、未知格式或含凭据地址当成合法来源。输出仅解释已记录信息，不证明当前包字节、编译成功或来源真实性。

按[团队任务示例](../examples/team/README.md)分别生成发布目录与全新的消费目录。由受保护环境注入角色令牌，不把发布令牌配置到只读CI任务；各任务隔离HOME与缓存，消费端使用独占私有命名空间路由。任务机需已有Linux仓颉SDK、增强版cjpm及本机编译链接工具，离线服务端包不包含工具链。

消费任务先构建，再直接运行默认产物，任一步失败即返回非零；成功后保存锁文件及来源记录，检查运行输出。来源记录在构建失败时也可能存在，不能单独作为CI成功依据。当前验证使用已有Docker引擎的内部服务名网络，不等于跨主机或公有云CI验收。

运行状态修订后的客户端 `cjpm run` 在应用非零时返回1，不再错误报告成功；成功仍返回0。若CI需要精确区分应用自己的7等退出码，仍采用上面的构建后直接执行方式。旧af35及此前客户端未包含该修订，应核对实际交付包摘要。

使用HTTPS地址前先阅读[客户端身份与CA说明](https-client.md)。当前本地修订在默认严格模式下验证DNS名称或IP SAN，CA路径在Linux任务子进程中提供；旧客户端只验证证书链的行为已有实际缺口。实际团队反向代理及跨主机HTTPS仍需单独验收。

## 升级前保留什么

当前交付组合与已执行/尚未执行范围统一见[固定候选验收清单](candidate-acceptance.md)；历史恢复、容量和平台验证绑定各自产物，不能按文档中“当前”字样继承到新版本。

增量链接修复会通过内部缓存版本使旧静态构建记录升级一次，通常会重新编译/链接相关产物；已实测保留旧target直接升级，无需把删除target当作修复。原锁文件、配置及来源记录仍应按下面清单保留。此验证覆盖命名仓换地址及静态传递链接，不承诺任意同路径保留全部时间戳的编辑均可识别。

具体维护顺序、兼容降级与快照回退的区别，见[单实例升级与回滚](upgrade-and-rollback.md)。当前b3ce/5f8f到bad0/8fc3已独立完成隔离演练14/14（16.36s）；恢复升级前快照不会保留快照之后的发布，不等于任意版本无损回滚或实际业务切换已完成。该数据演练不迁移CA/Compose配置，也不执行客户端编译；旧组合记录保持其原身份。

命名仓/多仓客户端新增URL缓存分区时，需要一次在线预热：旧名称目录缺少可靠的地址绑定，不自动迁入新分区，也不删除原缓存。命名仓缓存现在位于 `repository/registries/<名称>/<原始URL的SHA-256>/`；相同配置名称换地址会隔离索引与源码，切回已预热的地址可按已有策略离线复用。请在离线演示或升级切换前先验证所需地址的分区已预热。仅单个 `repository.home` 保持旧布局，其地址变化仍须换新的缓存根目录；详细契约见[多仓实现说明](multirepo-implementation.md)。

- 当前源码状态或版本、实际二进制 SHA-256，以及对应 SDK/stdx 版本；
- 仓库完整的 `index` 与 `artifacts`，同时保留其组织子目录；
- 部署参数及独立保管的令牌，不只保存一个状态文件；
- 升级前的诊断结果，以及正在运行的 Mirror/Sync 清单。

停止服务和会写入同一存储的 watcher 后，再做冷备份。只复制索引或只复制制品不构成完整备份。Docker 应备份实际持久化卷，不以镜像或容器文件系统代替包数据。当前没有自动备份调度和事务快照工具，不能据此承诺不停机备份一致性。

## 恢复到独立目录

1. 保留故障现场，停止确认属于本部署的服务及 watcher。
2. 将完整备份恢复到新的空目录或独立卷，避免直接覆盖故障数据。
3. 使用对应平台的服务端产物启动恢复副本。Windows 可用 `start.ps1 -Storage <恢复目录>`；需要并存检查时另选端口。不要共享两个进程的可写存储。
4. 运行诊断，读取默认仓与所用组织仓的索引、制品，并将下载 SHA-256 与备份索引比较；验证需要使用的客户端项目后，再安排切换。
5. 保留原目录与备份，直至恢复结果经实际业务检查。

上述文件存储冷备份流程已在 Windows 与 Linux 各完成一次独立演练：使用真实 cjpm 包，停服后复制完整存储并核对文件集合与 SHA-256，使原路径离线，再从新目录恢复；验证私有读取、默认/命名组织包、全新缓存下构建运行、再次发布和重启持久化。复验入口见 [冷备份恢复专项](../integration-tests/recovery/README.md#cold-filesystem-backup-and-restore)，实际产物与证据见 [验证报告](verification-report.md)。

演练的清单对比能发现测试副本的制品损坏和索引缺失，不代表服务提供自动备份校验。凭据与部署参数仍需独立保管。

含CA的新离线部署应同时保留三部分：可信渠道取得且清单校验通过的完整七文件包、原受保护 `.env` 与 `trust/ca.pem`（未配置CA时为空trust目录）、停服后的完整数据卷备份。不要只备份数据卷或只保存CA摘要；缺少原令牌可能使客户端无法认证，缺少实际CA则不能重建HTTPS信任。备份配置含凭据，保护其访问权限，不能放到公开仓库或与普通日志一起分享。恢复到其他目录时须检查CA实际字节及只读挂载，保留原始备份，再做真实客户端冷构建。

当前bad0/8fc3完整七文件CA离线包和完整8da5客户端已独立完成15阶段隔离演练（58.31s）：源停服后配置/CA及数据备份、新项目/新卷恢复、标准Compose运行诊断、原令牌私有读取、原服务及HTTPS上游离线下空缓存实际构建运行、重建和源/备份保持。客户端为默认模式，未启用来源基线；历史b3ce/5f8f与6a7客户端记录另行保留。入口见[CA配置冷恢复专项](../integration-tests/recovery/README.md#portable-ca-configuration-and-data-cold-restore)，准确身份及范围见[验证记录](verification-report.md)。脚本只接受新合成测试安装，不直接备份或切换现有业务；使用新项目名是为了隔离演练，不是已实现自动迁移。

Docker 命名卷另已完成停服 tar 导出、新卷恢复及真实客户端构建的独立演练（9/9）；流程与复验入口见 [Docker 部署说明](../deployment/docker/README.md#冷备份与恢复验证)。演练不操作现有业务卷，也不执行业务切换。在线快照、自动调度、业务切换和断电持久性尚未验证。

宿主不能执行仓颉程序时，恢复演练也可用 `--client-bundle` 搭配已有Linux SDK及任务工具，在容器内运行完整客户端包。制作包的任务断网，恢复后的两个消费任务通过恢复容器内部网络读取，不改变宿主回环监听或防火墙。具体参数和工具依赖见[恢复入口说明](../integration-tests/recovery/README.md#docker-volume-cold-backup)；这个入口只操作新建测试卷，不能直接用于现有业务卷。

## 按故障类型处理

| 现象 | 检查与操作 |
| --- | --- |
| 启动提示端口占用或进程身份不符 | 核对占用者、路径和启动时间，不删除活跃状态文件来绕过检查；旧状态迁移见 Windows 部署说明 |
| 401 / 403 | 检查源读取、目标读取和目标发布令牌各自用途，不通过公共仓回退绕过 |
| 仓库返回重定向 | 配置直接可用的仓库端点，核对反向代理是否在重写协议或主机；客户端不会自动转发包体或切换仓库身份，不通过关闭strict-tls处理 |
| 404 / 5xx | 用 `cjpm repo doctor <包名>` 查看各允许仓库；独占路由不会跨仓回退 |
| 网络超时、连接失败或响应损坏 | 修复网络或上游响应后重试；这些错误当前停止解析，不隐式切换来源 |
| 发布中断 | 重发同一版本及相同内容。只有匹配的索引/制品缺失状态可补齐，完整重复和冲突仍返回 409 |
| Sync 中断或响应丢失 | 重跑原条目或清单。目标完整时跳过，缺失制品可补齐；损坏或冲突内容明确失败，不自动覆盖 |
| 历史来源地址不安全 | 保留原记录，在配置中移除 URL 凭据，改用 `token-env`，成功构建后重新生成来源记录 |
| 原生服务端或 Mirror/Sync 提示 invalid URL | 使用无凭据、查询参数和片段的 HTTP(S) 基地址；认证改用相应 `CJREPO_*TOKEN` 环境变量；非法地址的 watcher 会直接退出，修正配置后再启动 |
| 同名命名仓改为另一个URL | 新URL自动使用独立缓存分区，首次需联网；旧分区保留，不自动迁移。若使用旧版客户端，仍须更换名称或缓存根目录 |
| 旧单仓 `home` 改URL或从多仓切回该模式 | 仍使用兼容布局；换新的缓存根目录，避免命中旧地址内容 |

`cjpm repo explain <包名>` 是单包候选预览，忽略cjpm.lock及传递约束；例如锁定构建用1.0.0时，在线预览仍可能显示2.0.0。`--recorded` 读取已保存的实际依赖解析记录，不代表实时仓库状态，也不是官方lockfile或编译成功回执。依赖解析和下载成功后即可能更新记录，后续编译仍可能失败；解析阶段遇到401时，可以保留之前那份历史记录，需结合本次命令退出状态阅读。

`repo doctor`按路由允许的顺序逐个探测元数据，可能更新本地索引缓存；它不是构建模拟，不下载制品，也不证明完整图能求解或应用能运行。即使某仓401/403阻止实际解析回退，doctor仍独立检查其他允许仓，任一元数据检查失败时整体非零退出。对失败的元数据检查，新版源码的Fallback ALLOWED还要求存在剩余允许仓：独占路由、禁用后无下一仓及最后一仓的404/5xx均显示BLOCKED并说明无剩余路由允许仓；状态码本身禁止回退时同样BLOCKED。

当前固定5dd187b5团队包已包含上述诊断修复，包内启动器定向11项通过。保留的f433旧包在无下一仓的404/5xx时可能仍显示ALLOWED；使用旧包须核对路由和实际允许仓列表，其实际路由/认证阻断未放宽。完整身份与各自验收边界见[候选入口](candidate-acceptance.md)。

离线读取只支持 `formatVersion = 1`。若提示 `unsupported repository provenance format version`，原记录会保留：先核对生成记录与读取记录的客户端版本，使用匹配的客户端；或在保留原记录副本后，由当前客户端重新构建生成记录。不要仅修改版本号来跳过格式检查，也不要把重新生成记录视为编译已成功。

HTTP400错误正文若包含当前仓库配置的完整令牌，客户端会将该值替换为 `[REDACTED]`，同时保留状态码及其他详情。此检查覆盖索引诊断、包下载和发布的JSON/纯文本错误出口；不保证处理编码后的令牌、其他敏感字段或所有异常路径。原始日志仍需按敏感材料保管，公开前核查，不以该局部保护替代日志审查。

新Linux服务端的Proxy/Mirror/Sync读取及Sync发布也不自动跟随跳转，包括同源跳转。Proxy传递上游非200状态且不填充缓存，Mirror/Sync返回失败；遇到3xx应调整直接仓库端点。需要跳转的服务不再沿用旧默认行为，禁止用目标返回200或已移除认证头作为允许转发发布包体的依据。具体产物身份与本机HTTP验证范围见[验证记录](verification-report.md)。

新Linux服务端的出站TCP连接默认30秒/次，可在启动前设置 `CJREPO_CONNECT_TIMEOUT_SECONDS` 为1–300的整数。非法/空值在主入口退出2，诊断不显示原值。原生进程设置环境变量；离线容器应修改本部署受保护.env，再按[离线包说明](../deployment/portable/README.md)重建服务以生效，不能只设置宿主变量。连接超时后先核对端点和网络可达性，再重试；不要仅增大期限掩盖错误端点。原stdx15秒读写期限不变，此项不限制DNS、TLS握手、整个同步或watcher总时长。

Proxy索引缓存TTL使用 `CJREPO_PROXY_TTL_SECONDS`，默认86400秒，合法0保留；负数、非数字和Int64溢出使用86400并警告。新5f8f服务端警告不回显原输入，避免误填内容进入日志；这不同于TCP期限的非法值退出策略，也不保证其他配置/所有日志均脱敏。旧归档不会自动获得此修复，领取新完整包并核对摘要。

当前fa00服务端保留`CJREPO_MAX_ARTIFACT_BYTES`（默认134217728、范围1–1073741824）及上游`CJREPO_MAX_INDEX_BYTES`（默认4194304、范围1–67108864），并新增每组织/包Hosted发布累计索引的`CJREPO_MAX_HOSTED_INDEX_BYTES`（默认4194304、范围1–67108864），均为字节。旧索引读取及追加按实际UTF-8字节检查，含分隔符和换行，精确上限接受，超限413且不写新制品/索引；重复/冲突409和不追加索引的缺失制品恢复保持。降低上限后超过限制的历史索引不截断/删除，读取接口不改；应先备份并核对规模，在允许范围调整，不能自动清理或忽略拒绝。空/非法值入口退出2且不回显原值，修改受保护.env后须重建容器。旧8fc3镜像不支持此新增上限，回退时需明确该边界。完整说明见[新包教程](../deployment/portable/README.md)，当前身份与独立实测范围见[候选入口](candidate-acceptance.md)。这些仍不是总内存、全局并发/磁盘配额、流式落盘或完整操作时限。

当前fa00服务端另有`CJREPO_MAX_CONCURRENT_PUBLISHES`，默认8、范围1–64；空或非法值启动退出2，不回显原值。它在方法/发布鉴权通过后、读取请求体前限制单进程所有组织/包的已准入发布处理器，满额立即429并返回`Retry-After: 1`、`Connection: close`；没有排队或自动重试。持有者在成功、重复/格式/摘要/大小错误、存储失败或连接中断后经finally释放，拒绝者不释放他人的名额。慢请求仍可持有名额至连接结束/既有传输行为触发，不增加完整操作总期限，也不是总连接数、Proxy读取、精确总内存或磁盘配额。此项现已装入f640镜像及完整新包；旧63ce/3348包不支持，回退后失去限制。身份及独立验收范围见[验证记录](verification-report.md#2026-10-25-发布并发限制固定包验收)。

Proxy/Mirror/Sync使用HTTPS上游或目标时，先按[CA说明](https-client.md)核对主机名/IP SAN和可信CA。Linux进程可用 `SSL_CERT_FILE`；新七文件包首次配置可用 `configure.py --ca-file` 导入PEM证书，固定只读挂载并记录摘要，旧.env/trust不覆盖。不导入CA时只有空trust、未预装公共根CA，宿主文件路径不能直接当容器路径。运行诊断检查宿主/容器证书内容与只读属性，发现篡改或缺元数据应先保留现场；不要通过重新初始化或关闭校验掩盖问题。此流程仅新安装，不提供原安装CA轮换/迁移；出站HTTPS不改变服务端HTTP监听入口，仍不代表入站网关或跨主机验收。

## 停止与卸载

Windows 使用 `stop.ps1`，Docker 使用 `down.ps1`，默认保留包数据。卸载程序前核对存储实际位置并保留备份。Docker 的 `-PurgeData` 会删除持久化数据，不用于普通升级或排障。

每批产物的实际通过范围与未验证事项见 [验证报告](verification-report.md)，不能把历史测试记录视为当前版本验收。
