## 一 项目概述

1. 项目一句话定位：CjRepoMesh 为仓颉原生 cjpm 增加可配置的多仓依赖来源，并提供轻量私有中心仓的 Hosted、Proxy、Mirror 和仓间 Sync 闭环，使企业内部包与公共依赖可以在明确的安全边界内构建和审计。
2. 项目开发背景：单一公共仓无法容纳不能公开发布的内部包。简单按优先级逐仓查找又会让旧版本覆盖新版本，认证失败时回退公共仓还可能引入同名包劫持。项目在原 cjpm 求解器之外增加仓库路由和来源层，不改写版本约束与冲突规则。
3. 项目核心目标：基础能力是命名仓库、优先级、禁用仓、令牌环境变量、跨仓候选聚合、同版本来源确定和私有仓部署。进阶能力是独占命名空间、401/403 阻断、来源及 SHA-256 审计、并发安全代理缓存、校验后镜像与增量同步。

## 二 需求分析与适用人群

1. 目标用户：管理企业内部仓颉包的服务端团队、同时使用公共与私有依赖的应用团队，以及需要离线构建或包来源审计的研发/教学团队。当前证据基于本地 Linux、Docker 和历史 Windows 环境，不宣称已在鸿蒙设备部署。
2. 开发痛点：内部包不能直接放入公共中心仓；单仓故障影响构建；单纯仓库优先级可能改变版本求解结果；同名高版本公共包会威胁私有命名空间；离线缓存与同步若没有校验，难以证明制品来源和完整性。
3. 对应方案：命名仓库和路由解决来源管理，候选版本聚合后仍交给原求解器解决版本/冲突；`exclusive` 路由和认证失败阻断保护私有包；Proxy 校验缓存及清单式 Mirror/Sync 提供离线复用；`repo explain`、`repo doctor` 与独立来源审计文件提供可观察性。

## 三 作品核心能力与功能设计

1. 基础能力一：多仓解析。应用通过 `cangjie-repo.toml` 声明仓库 URL、优先级、`enabled`、`token-env` 和路由规则。Router 聚合允许仓库的候选版本，原 cjpm 求解器选最终版本，同版本再按优先级确定来源。端到端测试证明高优先仓有 1.0.0、低优先仓有 2.0.0 时，最终仍选择兼容的 2.0.0。
2. 基础能力二：私有仓服务。Docker Compose 在本机端口启动 CjRepo Server；Hosted 提供发布、索引和制品下载，Proxy 缓存已校验的上游索引/制品，Mirror/Sync 按清单批量处理包。真实 cjpm 已完成组织包发布、拉包编译、源仓离线后目标仓构建。
3. 创新点一：版本求解与仓库来源解耦。跨仓候选版本不会因仓库优先级而提前剪枝；保留原生 `[replace]` 和传递依赖冲突语义。相较于顺序查找仓库，这避免了旧版高优先仓错误覆盖新版依赖；来源与 SHA-256 可独立审计。
4. 创新点二：安全感知回退。`company::*` 独占路由不会访问公共仓；私有仓返回 404/401/403/500 时，公共仓请求数实测均为 0。普通依赖的 401/403 也阻断向低优先仓回退，防止认证失败被误当成“包不存在”。

## 四 仓颉语言核心特性应用

1. 模块化与接口实现：服务端将 HTTP 分发、Hosted、Proxy、存储和同步分为仓颉源文件；`PublishHandler`、`ProxyIndexHandler` 等类实现 `HttpRequestHandler`，将请求入口与存储操作解耦。代码见 `server/src/main.cj`、`hosted.cj`、`proxy.cj`。
2. 并发同步：`server/src/storage.cj` 建立 256 路有界 `Mutex` 锁分片；`hosted.cj` 与 `proxy.cj` 通过 `synchronized(packageStorageLock(...))` 保护同包发布和首次填充，同时允许不同包在不同锁分片上并行。测试覆盖同包并发原子性与不同包慢上游并行；哈希碰撞仍可能导致无关包串行。
3. 异常与类型约束：服务端针对包名、版本、索引、校验和与网络错误使用显式类型及 `try/catch`；不合法组织名在访问上游前拒绝。`sync.cj` 对清单逐项处理并汇总部分失败，避免单项错误伪装为全量成功。
4. 技术栈：仓颉 Compiler 1.1.3、stdx 1.1.3.1、原生 cjpm；Windows PowerShell 与 Python 标准库主要负责部署和跨平台测试编排，服务核心与增强客户端为仓颉代码。Linux 验证环境为 WSL 2 Ubuntu 22.04.5；Docker 镜像基于 Ubuntu 22.04。

## 五 性能与兼容性设计

1. 性能：Proxy 在相同本机 HTTP 夹具下，10 轮冷请求 Median 62.76 ms、50 轮热请求 Median 33.102 ms，Median 比值约 1.9 倍。结果只说明本机已校验缓存路径比冷填充路径快，不代表公网官方仓延迟或跨机收益。原始样本和方法见 `benchmark/results/proxy-benchmark.json` 与 `.md`。
2. 兼容：服务端和增强版 cjpm 在 Cangjie 1.1.3 Linux 上完成四组端到端回归；官方 Maple 本地子集分别在原版与增强版通过。Docker Doctor 9 项通过。Windows 历史五组通过，但当前本机的未签名 SDK 被 Code Integrity 拦截，不能宣称当前提交 Windows 复测通过；完整官方 HLT/LLT 也尚未运行。
3. 稳定与容错：发布拒绝错误令牌、错误 SHA-256 与重复版本；Proxy 拒绝损坏制品且不会缓存；Sync 对相同 SHA-256 跳过，对不同 SHA-256 冲突拒绝覆盖。Docker 默认非 root、只读根文件系统、丢弃 capabilities、仅绑定本机端口，持久化卷重建后保留包和校验和。

## 六 使用说明与落地场景

1. 快速接入：按 `README_CJREPOMESH.md` 配置 `cangjie-repo.toml`，按 `deployment/docker/README.md` 启动 Compose，运行 `deployment/docker/doctor.ps1` 检查 9 项；私有令牌由被 Git 忽略的 `.env` 或环境变量提供，不写入仓库。跨平台回归入口为 `integration-tests/run-linux.sh` 与 Windows 对应脚本。
2. 落地场景：企业研发团队把内部包托管在 Hosted，公共包经 Proxy 缓存；内网环境按显式清单镜像所需版本，或从一个 CjRepo 同步到另一个 CjRepo；离线构建时使用已校验缓存，并由 `repo explain` 核对实际来源。
3. 核心价值：减少手工切换仓库与重复搭建私有包服务的工作；在私有命名空间和认证失败场景下保住来源边界；保留原求解器规则并给出可核验的包来源。当前未收集真实企业用户的长期使用反馈，不对生产规模或商业收益作定量承诺。

## 八 作品总结与未来展望

1. 项目总结：CjRepoMesh 将多仓来源路由与原 cjpm 依赖求解分层，配合私有 Hosted、Proxy、清单 Mirror、增量 Sync、来源 SHA-256 审计，解决内部包托管、离线依赖和安全回退问题。当前证据证明本地端到端可运行，不等于长期生产稳定性或完整官方兼容认证。
